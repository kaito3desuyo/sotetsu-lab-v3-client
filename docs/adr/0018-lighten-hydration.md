# ADR-0018: SSR の後のブラウザの仕事（hydration）を軽くする

- **日時**: 2026-10-28
- **Agent**: claude-opus-5-5
- **ステータス**: 採用済み
- **ブランチ**: perf/hydration-recompute
- **関連**: ADR-0014（SSR の描き分けの決まり）、ADR-0017（SSR を Lambda で動かす）

---

## 背景

- SSR にしても、ブラウザは hydration で画面の computed を全部計算し直し、サーバーが描いた DOM を全部たどる。その間は操作が効かない。駅別時刻表は SSR の TBT が SPA より悪かった（2.0 秒と 1.7 秒。ADR-0017 の結果）。
- 手元の SSR（ソースマップ付き）を、スマホ相当（412×823・CPU 4 倍遅く）で開いてトレースを取り、CPU プロファイルを元のファイルに戻して内訳を見た。
- 仕事は 3 段に分けた（ユーザー判断・2026-10-28）。1. ブラウザでの計算のやり直しをやめる。2. 描く量を減らす。3. 全画面に共通の土台を軽くする。この ADR は 1 と 2 の分。

## 決定

### 1. 計算のやり直しをやめる

- **全線時刻表の並べ替え（`sortTrips`）を速くする**。並びは変えない。駅を番号にして、時刻を数値の配列で持つ。局所探索の中で配列を作り直さない。実データ 7 通りで、前と同じ並びになることを確かめた。2〜3 倍速い。
- **全線時刻表の並び順は、サーバーから渡す**（`TransferState`・キー `timetable-all-line-order`）。サーバーは並べた列車ブロックの ID の列を入れる。ブラウザは最初の 1 回だけそれで並べ、使ったらキーを消す。
  - ダイヤ・方向・本数・ID が今の中身と合わないときは、今までどおり並べる。
  - HTML は圧縮後で +1.6KB。ブラウザの並べ替え 167〜172ms が 0 になった。
  - 他のページには広げない。ダイヤグラムの線は大きく（HTML 4.3→5.5MB）、トップの列車位置は時刻で変わる。駅別と運用表は、計算ではなく描く量が重い。
- **時刻データの組み直しとダイヤグラムの線では、オブジェクトの展開（`{ ...a }`）を使わない**。項目を書き並べ、型は `AllKeys<T>`（`core/utils/all-keys.ts`）で受ける。項目の足し忘れは型で止まる。
  - `@angular/build` は esbuild に `'object-rest-spread': false` を渡す（V8 の不具合 11536 を避けるため）。だから `{ ...a, b }` は遅い補助関数（`__spreadProps` = `defineProperties`）になる。設定では切れない。
  - Node で 3 万件を測ると、補助関数 82ms・素の展開 10ms・書き並べ 0.4ms だった。
  - 熱い所（件数 × 呼ばれる回数が大きい所）だけに使う。他は今の書き方のままでよい。

### 2. 描く量を減らす

- **駅別時刻表の時の行は、セルの格子を `@defer (on viewport; prefetch on idle; hydrate on viewport)` で包む**。サーバーは今までどおり全部描き、ブラウザは画面に入った行から hydrate する。時の数字の列（貼り付く紺の帯）は `@defer` の外に置く。
- **559px 以下では、時の行に `content-visibility: auto` と見積もりの高さ（`contain-intrinsic-size`）を付ける**。画面外の行は、レイアウトも描画もしない。
  - 559px は格子が必ず 1 列になる幅。それより広いと列数が変わり、見積もりが合わないので付けない。
  - 見積もりは `utils/station-row-height.util.ts`。2026-10-28 に各セルの高さを測って式を決めた。
    - セルの高さは、左の列（分・運用・編成）と右の列（↪ の数）の高い方。
    - 今日のダイヤ・過去のダイヤ・別の駅のどれでも、全体の差は 0.5% 未満、1 行の差は最大 9px だった。
  - スクロールバーで一気に飛ぶと、行き先が 1% ほどずれる（20,000px 送って約 200px）。描く前の行は見積もりの高さなので。普通にスクロールするぶんにはずれない。
- **HTML には全時刻が残る**。だから検索（クローラー・ページ内検索）は変わらない。サーバーで最初の数時間だけ描く案は、時刻が HTML から抜けるので採らなかった。
- **運用表でサーバーが中身まで描くカードは 8 枚から 4 枚にする**（ADR-0017 の 8 枚を改める）。
  - カードは縦に長い。1440px でも 1 段目の 4 枚だけで画面が埋まる。読み込み後の画面は、412px・1440px とも前と同じだった。
  - 5 枚目からのカードは検索に載らない。
- hydration の前に Angular が文書の全コメントをたどる処理（`processTextNodeMarkersBeforeHydration`）は、コメントの数に比例して重い。駅別ではコメント 4,649 個で 0.31 秒、運用表では 3,839 個で 0.26 秒かかった。サーバーが描く DOM を減らすと、ここも減る。

## 結果

スマホ相当（CPU 4 倍）の TBT。手元の SSR で 2〜3 回測った。

| ページ | 前 | 段 1 の後 | 段 2 の後 |
|---|---|---|---|
| 駅別時刻表 | 3.63 秒 | 3.04〜3.46 秒 | 1.56〜1.71 秒 |
| 全線時刻表 | 1.88 秒 | 1.26 秒 | （段 2 は無し） |
| ダイヤグラム | 2.35 秒 | 1.94 秒 | （段 2 は無し） |
| 運用表 | 1.53 秒 | 1.35〜1.51 秒 | 1.21〜1.28 秒 |
| トップ | 1.58 秒 | 1.30 秒 | （段 2 は無し） |

- 段 1 の後でも、サーバーが描いた HTML は前と同じだった（部品の通し番号を除く）。スクリーンショットも同じだった。
- 段 2 の後、駅別の HTML の時刻（分）の並びは前と完全に同じだった。画面に入った後から hydrate した行の列車番号のリンクも、押して全線時刻表へ移れた。
- 残りは全画面に共通の土台（zone.js・header・sidenav・GA・localforage。どの画面でもそれぞれ 0.05〜0.18 秒）。これは段 3 でやる。
