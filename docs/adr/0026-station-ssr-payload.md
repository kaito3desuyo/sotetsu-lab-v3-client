# ADR-0026: 駅別時刻表の SSR に積む trip-blocks を、描く分だけに削る

- **日時**: 2026-11-16
- **Agent**: claude-sonnet-5-5
- **ステータス**: 提案（駅別時刻表の検証まで。全線時刻表・運用表は未着手）
- **ブランチ**: perf/ssr-payload-trim
- **関連**: ADR-0017（SSR on Lambda）、ADR-0025（ルートの chunk の先読み）

---

## 結論

- 駅別時刻表の `ng-state` は、5 駅・上り下りの 10 通りで 2.43〜2.45MB から 0.33〜0.71MB に減った。HTML 全体は 2.9〜3.9MB から 0.8〜2.2MB に減った。
- `main` の `innerText` は、hydration 直後も全量を取り直した後も、変更前と全文一致した（8 通り）。駅を 7 回続けて替えても欠けた列車の行は出ず、ページの例外は増えなかった。
- 計画の目標（0.3MB 未満）は、新宿（0.33MB）でも届かなかった。差の大半は、trip-blocks 以外の応答（駅一覧・路線一覧など約 250KB）が占める。採用の可否は、この差を許せるかで決める。

## 背景

- 駅別時刻表の SSR は、trip-blocks の全量（方向ぶん・約 2.2MB）を `HttpTransferCache` 経由で HTML に積んでいた。描くのはその駅に停まる列車だけなので、残りは HTML を重くするだけで、初回の JS の開始を遅らせる。
- 変更の中身は、全量の GET を `SKIP_TRANSFER_CACHE` で転送の対象から外し、その駅に停まる列車を持つ運行だけ・時刻は 3 つまで（`stopSequence` の最小・最大・その駅）に削った配列を、専用の鍵 `timetable-station-trips` に積むこと。ブラウザは、暦・方向・駅が合うときだけこれで描き、描いた後の idle に全量を取り直す。削った配列は `QueryCache` に入れない。

## 確かめ方

- 本番ビルド（`npm run build:ssr-check`）の SSR を 2 つ用意した。変更前は first commit（e1c87445）の別 worktree、変更後は変更を当てた worktree。どちらも本番の API を読むだけで、`TZ=Asia/Tokyo`、ポートは 4301（前）と 4302（後）。
- URL は `/timetable/station;calendar_id=<平日ダイヤ 2026-03-14>;station_id=<駅>;trip_direction=<0|1>`。駅は横浜・二俣川・海老名・湘南台・新宿。
- ブラウザの検証は Playwright（Chromium）。localhost から本番 API へは CORS で届かないため、`page.route` で本番 API の応答に CORS ヘッダーを足して中継した。取り直しの trip-blocks 要求は、`page.route` で止めて hydration 直後の状態を取り、離してから取り直し後の状態を取った。

| 二俣川 | 0 | 522 | 522 | 全文一致 | 全文一致 | 0／1 |
| 二俣川 | 1 | 417 | 417 | 全文一致 | 全文一致 | 0／1 |
| 新宿 | 0 | 292 | 292 | 全文一致 | 全文一致 | 0／1 |

| 湘南台 | 0 | 373 | 373 | 全文一致 | 全文一致 | 0／1 |

- 0 時台の列車を持つ駅（二俣川・海老名・湘南台・横浜・新宿の下り）も含めて一致した。
- 変更前は、描いた後に trip-blocks を取り直さない。変更後は idle に 1 本取り直す。取り直し後も行数と中身は変わらなかった（取り直しの要求は、止めて離すまでの間も 1 本のまま）。
- 横浜・下りの 1 件だけ、3.5 秒待った時点で取り直しの要求がまだ出ていなかった（idle は遅れて来ることがある）。離した後の 4 秒の内に 1 本出て、中身は一致した。

### 3. 駅の切り替え

二俣川（上り）から、希望ヶ丘・三ツ境・瀬谷・大和・相模大塚・さがみ野・かしわ台の順に、前後の駅のボタンで 7 回替えた。各回の `main` の `innerText` を、変更前の同じ操作と比べた。

| 条件 | 7 回の本文 | 最後（取り直しを離した後） | trip-blocks 要求の合計 |
|---|---|---|---|
| 変更前 | 基準 | 基準 | 0 |
| 変更後・取り直しを止めたまま替える | 7 回とも全文一致 | 全文一致 | 1（止めた取り直しだけ） |
| 変更後・取り直しが済んでから替える | 7 回とも全文一致 | 全文一致 | 1 |

- 行数は 339・358・365・616・379・358・411 で、前後とも同じ。欠けた列車の行は出なかった。
- 取り直しを止めたまま 9 秒以上替え続けても、替えるたびの追加の要求は出ず、本文は全量のときと同じだった。止めた応答が戻った後も本文は変わらなかった。
- 止めている間に追加の要求が出ないのは、駅の切り替えの取得が、取り直しと同じ鍵の `QueryCache`（`shareReplay`）を引き、止めた 1 本を一緒に待つためである（service を読んで確かめた）。応答が戻ると、`fetchTrips` の tap が呼んだ時と今の駅を比べ、古い駅の分は書かずに今の駅の分だけを書く。

### 4. 例外

- 全 8 通りの hydration と、駅の切り替えの全回で、`pageerror` は 0 件。
- コンソールのエラーは、変更前後とも同じ 401（1 ページあたり 1〜3 件。検証用の中継に認証の Cookie が無いことによるもので、変更の影響ではない）。
- 両サーバーのログに、起動の 1 行以外は出なかった。

## 結果として残る課題

- `ng-state` は 0.3MB 未満に届かなかった（新宿 0.33MB・二俣川 0.7MB）。残りは trip-blocks 以外の応答と、残した運行の列車が持つ項目（`tripOperationLists` など）。これを削るなら、削る項目を決める別の判断が要る。
- 取り直しの要求は、描いてから約 2〜4 秒後に出た（手元の計測）。この間の列は削った配列で描いた分で、見た目は同じだが、取り直しが失敗すると削った配列のまま残る（行は正しい）。
- 検証していないこと: 390px・1440px のスクリーンショット比較、実機の ng-state の転送時間の差（HTML の転送量は減るが、Lambda の応答時間は測っていない）。

## 全線時刻表と運用表（2026-11-16 追記）

全線時刻表は並べ替えた順の 1 ページ目（既定の絞り込みで隠れる列車は数えない）の運行だけを、運用表は先頭 4 枚の運用をそのまま・5 枚目からの列車を場所取りに要る 5 項目だけに削って積む。どちらも全量は hydration の直後に取り直し、届くまでは `isPartial` を立てる。

手元の本番ビルドの SSR（平日ダイヤ・API は本番）で、変更前と変更後を比べた。

| ページ | ng-state（前 → 後） | HTML 全体（前 → 後） |
|---|---|---|
| 全線・上り | 2,479KB → 274KB | 2,922KB → 717KB |
| 全線・下り | 2,504KB → 263KB | 2,946KB → 705KB |
| 運用表 | 1,269KB → 626KB | 1,904KB → 1,261KB |

- 全線・上りの `main` の本文は、hydration の直後も取り直した後も変更前と全文一致した。
- 全線・上りで hydration の直後（0.8 秒後・取り直しの前）に次のページへ送り、12 秒後の本文が変更前の同じ操作と全文一致した。
- 全線・下りの body の本文と表の行数（40 行）が、変更前と一致した。
- 運用表は、2 往復ゆっくりスクロールして全部のカードを描かせると、変更前も変更後も 52 枚で、カードの中身が全文一致した。速くスクロールすると、画面に入ったときに描く 5 枚目からのカードの一部が描かれず、どのカードが出るかが前後で 1〜2 枚ずれた。ゆっくり全部描かせると一致したので、描く間合いの差と見ている（変更前どうしで同じずれが出るかは測っていない）。
- どの回も `pageerror` は 0 件だった。
- 確かめていないこと: 運用表の運用群の選択を替えたとき、全線の路線の絞り込みと方向を取り直しの前に替えたとき（spec では確かめた）、土休日ダイヤ。
