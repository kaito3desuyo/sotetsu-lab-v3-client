# 編成の記録（M14 段 1）設計

## 目的

推しの編成がある常連が、その編成が最近どの運用に入っていたかを眺めるページを作る（ユーザーの言葉で「推しの編成の最近の動きを眺める」）。

目撃は十分に濃い。2026-11-19 の本番では、145 編成のうち 123 本がこの 30 日に目撃されていた。真ん中の編成は 30 日のうち 23 日、1 年のうち 269 日の目撃がある。日ごとの運番をカレンダーに並べれば、動きが見える。

## 段の分け方

M14 は 2 段に分ける（ユーザー了承）。

- 段 1（この設計）：月のカレンダーと、今日（いなければ最後に見た日）の運番。編成の組成・組み換えの履歴・編成が解かれた日を車両の絵で出す（2026-11-21 にユーザーが段 1 に入れると決めた）。api には、期間の取得に編成の絞り込みを 1 つ足し、車両の改造の記録を持つ表を足す
- 段 2（別の設計）：路線・直通先ごとの割合。api に集計の口を作ってから足す。「直通先」を何と数えるか（JR に 1 往復だけ行った日を JR の日とするか、など）は、段 2 で決める

M31 の共有画像（編成と今日の運番が入ったカード）も、段 1 には入れない。

改造の記録を入力する管理画面（MANAGER 向け）は、段 1 のすぐ次の段にする（2026-11-24 ユーザー了承）。段 1 では表と読み取りを作り、値は SQL で入れる。管理画面の段で、編成の集約をまとめて保存する書き込みの api と、client のページを作る。

## 作り方の比較

| 案 | 中身 | 採否 |
|---|---|---|
| A. client だけ | 既存の期間の口で全編成のひと月分を取り、client で 1 本分を抜き出す。割合は運番ごとに列車を取りに行く | 不採用。この 30 日の目撃 3,776 件のうち 1 本分は 40 件で、99% を捨てる。割合には月 30 回ほどの呼び出しが要る |
| B. 専用の口を先に作る | 日ごとの運番と直通先を api がまとめて返す | 段 2 で採る。直通先の数え方を決めるまで、ページ全体が出ない |
| C. 2 段に分ける（採用） | 段 1 は既存の期間の口に編成の絞り込みを足して使う。段 2 で B の口を足す | 採用。眺める目的は段 1 で果たせる。推定の「?」は過去の運用と同じ仕組みで付き、ページによって扱いが割れない |

## 置き場と名前

- URL は `/records/formation;formation_number=10701;month=2026-11` とする（ユーザーが決めた）
  - `/operation/formation` は採らなかった（ユーザーが嫌った）
  - `/information/formation` は、M21 の運行情報と紛れるので採らなかった
- `records` は「目撃の記録から組み立てる、日々変わる情報」のまとまりにする。動かない資料を置く `/library/*` とは分ける。駅ごとの記録や、M22 の年ごとのまとめも、後からここに並べられる
- ディレクトリは `pages/records/records-formation/`（`pages/library/library-vehicle/` と同じ形）。route は `records.route.ts` に置く
- ページ名は「編成の記録」（私の判断。ユーザーが違えば直す）。ナビには「記録」の見出しを新しく作り、その下に置く。置く位置は「運用情報」と「ライブラリ」のあいだ
- 編成番号のリンク（`app-formation-number-link`、13 画面で使う）の飛び先は、今の編成別時刻表のまま変えない。編成別時刻表の見出しに、このページへのリンクを置く。ライブラリの車両ページからも、編成別時刻表を経て 2 回の操作で着く。roadmap の「ライブラリの車両ページとのつなぎ方」は、これで決着とする

## 画面

```
[操作帯] 編成番号 10701   ‹ 2026年11月 ›
─────────────────────────────────
10701 編成
今日 11/19  73 運用 → 編成別時刻表
─────────────────────────────────
 月   火   水   木   金   土   日
                          1    2
 71   72  73?   ··   41   42   43
 …
```

- 上の要約：今日の運番を出す。今日の目撃が無ければ、最後に見た日とその日の運番を出す。月を切り替えても、この欄は変わらない
  - 取り方は、カレンダーとは別に、既存の `GET /v3/operation-sightings/time-cross-section/formation-number/:formationNumber` を 1 回呼ぶ。この口は最新目撃のキャッシュ（`operation_sighting_latest_caches`）を引くので、何か月前の目撃でも返る。さかのぼる上限は設けない
  - 一度も目撃の無い編成は「目撃の記録はありません」と出す
  - 要約から、最後に見た日（今日の目撃なら今日）の属する月の `/records/formation` へのリンク「この月の記録」を張る。引退した編成が今の月の空のカレンダーしか開かないのを避けるため
  - 同日の引き継ぎで推定した運番のときは、`latestSighting` が元の目撃なので、運番は `expectedSighting.operation` の推定した今の運番を「?」付きで出す。推定できなければ「運用は不明です」と出す（real-time の編成カードと同じ規則）
  - api は、編成番号を渡されたとき、直接の目撃にも `operation` を付けて返す
- カレンダー：表示する月の各日に、その日に充当された運番を、受け持った順に並べる。推定（`includeCarriedOver` で付くもの）は、過去の運用と同じく「?」を付ける。無効化された目撃は出さない
  - 推定の写しは、元の目撃をそのまま写して運用だけを替えたもの（api の `sighting-carry-over.read-model.ts`）。だから「?」が付くのは、その編成自身の目撃から、同じ行程の後の運番へ引き継いだものだけになる。別の編成の目撃から付くことはない
  - 1 日に同じ運番の目撃が複数あるときの扱いと、並べる順は、過去の運用の 1 マスと同じにする。過去の運用のマスを作る処理（`operation-past-time` の utils）を、編成 1 本分に使えるなら使い回す。並べ順は api が返した順（受け持つ順）をそのまま使う
- 日付の境目は、ほかのページと同じく 4 時にする。「今日」と「今の月」も 4 時の境目で数える（11/1 の 2 時に開くと、今日は 10/31、今の月は 10 月）。client にある鉄道日の関数を使う
- 編成番号が無いときは、カレンダーを出さず、操作帯で編成番号を入力するよう案内する。どんな番号でもカレンダーを取りに行き、「編成が見つかりません」は出さない（client は全編成の一覧を持たず、引退した編成も見られるようにするため）。要約に最新の目撃が無いときは「目撃の記録はありません」と出し、打ち間違えた番号もこれで示す。目撃の無い月は、空のカレンダーに「この月の目撃はありません」と添える
- マスを選択すると、その日の編成別時刻表（`/timetable/formation;formation_number=…;date=…`）へ移動する。目撃の無い日は、選択できない形にする
- 月の切り替え：前の月・次の月のボタンを置く。今の月より先へは進めない。URL の `month` を書き換え、戻る操作で前の月に戻れるようにする。`month` が無いときは今の月を出す
- 編成番号の入力は、編成別時刻表の操作帯と同じ部品と振る舞いにする
- 狭い画面（375px）でも 7 列のカレンダーを崩さない。1 マスに運番が 3 つ以上あるときの詰め方は、作る側が実物で決める（[[project_design_principles]] の情報を削らない原則に従い、省略はしない）

## 見た目（2026-11-21 に実データの上で案を比べて決めた）

中身は 3 枚の白いカード（`tw-rounded-card tw-bg-white`）に入れ、上から見出し・編成の情報・カレンダーの順に並べる。カードの間は、ほかのページのカードと同じだけ空ける。

### 見出しのカード

編成別時刻表の見出し（`timetable-formation-header`）と同じ作りにする。

- 1 行目：編成番号を `tw-text-xl tw-font-bold`、その右に系列・会社を `tw-text-sm tw-text-muted` で「10000・相鉄」と添える。編成が解かれた日があれば「・2019/10/14 まで」と続ける。右端に「編成別時刻表」のリンクを置く
- 2 行目：「最後の目撃」（今日の目撃なら「今日の目撃」）を `tw-text-xs tw-text-muted` の見出しで出し、時刻・運番の札（`app-operation-number-tag`）・「で目撃」を続ける。言い回しは編成別時刻表に合わせる。今年でない日は年も出す
- 「この月の記録」は、最後に見た日の月と今見ている月が違うときだけ出す
- 系列・会社・解かれた日は、編成の取得（下の「編成の情報」）から出す。取れないときは番号だけを出す

### カレンダーのカード（B 案）

- カードの上端に、月の送り「‹ 10月　2026年11月　12月 ›」を置く。帯の中の送りも残す。送りのボタンは帯の中に置く決まり（docs/design.md）があるが、カレンダーの月見出しは表の一部として扱う。client の docs/design.md にこの例外を書き足す
- 曜日の見出しと日付の数字：土曜・日曜・祝日を赤（`--color-accent-deep`、太字）にする。土曜も赤にするのは、土休日ダイヤの日を色で見分けるため
- 祝日は、日付の右に祝日名を小さく添える。375px では祝日名を出さず、数字を赤くするだけにする。祝日は `calendar-dates` の口（`CalendarDateQuery.findMany({ from, to })`）で月ごとに 1 回取り、`memo` を祝日名に使う（ダッシュボードの `pick-day-name.util.ts` と同じ読み方）
- 今日：マスの地を `--color-paper-2` にし、日付の数字を紺（`--color-structure`）の丸で囲んで白抜きにする
- 罫線は `--color-rule` にする（今は `black/10` を直に書いている）

### 編成の情報のカード

車両を横から見た絵で、組成と組み換えの履歴を出す。絵は Wikimedia Commons の写真（ja.wikipedia の各系列の記事にあるもの）を見て描いた SVG で、写真そのものは載せない。

- 号車の順は `vehicle_formations.car_number` で並べる（api が返す順に頼らない）
- 組成：今見ている月の最終日（今の月なら今日）に有効な期間の組成を、号車の順に大きめの絵で並べる。絵の下に車両番号、その下に号車の番号を小さく出す。見出しは「組成」、横に「8両・下の数字は号車」と添える
- 組み換えの履歴：同じ編成番号の期間が 2 つ以上あるときだけ出す。新しい期間から順に、「2019/4/29〜2019/5/12　10両」の行と小さい絵の列を並べる。始まりの日が無い期間は「〜2019/4/28」と書く
  - 前の期間から入れ替わった車両は、番号を赤（`--color-accent-deep`）の太字にする。カードの下に「赤い番号は前の組成から入れ替わった車両です。」と添える
  - 各期間の絵は、その期間の最後の日（今も続く期間なら今日）の塗装で描く。期間の途中の塗り替えは、下の「改造の経歴」に出す
- 改造の経歴：編成の車両に記録された改造を、新しい順に並べる。1 行に、日付・種類（塗り替え・リニューアル・機器更新・ホームドア対応など）・中身・対象の車両を出す。編成の全車両に同じ日・同じ中身の記録があれば、対象は「全車」とまとめる。記録が無ければ、この欄を出さない
  - 出すのは、今見ている組成の車両の記録だけにする。編成を離れた車両の記録は出さない
- 1 両の絵：車体・屋根・帯・台車を描く（窓と扉は描かない。下の「外観」）。両端の車両は外側の端を、その形式の先頭の形にする。号車の数は期間ごとに 6〜10 両と変わるので、絵はカードの幅に収め、横にスクロールさせない。10 両で番号が入りきらないときは、番号の字を小さくする
- 1 号車がどちら側かはデータに無いので、向きは書かない
- 車両が 0 両の期間（3121〜3123 の 2099-01-01 の行など）は出さない。誤って登録された行で、本番の DB からはユーザーが消す
- 編成番号の期間が 1 つも取れないときは、このカードを出さない

### 外観（形式と塗装）

絵は形式ごとに分けて描く。同じ塗装の名前でも、形式によって車体の色・帯の位置・窓と扉の並び・先頭の形が違うため（2026-11-21 ユーザーの指摘「形式ごとに特色があるのだからちゃんと分けてよ」）。塗装も編成と時期で変わる（10701 は YNB、10702 はグループカラー。8000・9000・10000 は旧塗装からグループカラー、YNB へ塗り替えられてきた）。そこで、形式と塗装の組を 1 つの値（下の表の `livery` の値）にして、車両の改造の記録（下の「api の変更」）に種類 `livery` の行として持たせる。塗り替えたら、塗り替えた日の行を 1 つ足す。ある日の塗装は、その日までの `livery` の行のうち最新のものになる。

## api の変更（段 1）

### 車両の改造の記録

塗り替え・リニューアル・機器更新・ホームドア対応のような改造を、車両ごとに 1 回ずつ記録する表 `vehicle_modifications` を足す（2026-11-23 ユーザー。始めは `formations` に塗装の列を足す案だったが、見た目の変わらない改造も記録したいとして表に替えた）。

| 列 | 型 | 中身 |
|---|---|---|
| `id` | uuid | |
| `vehicle_id` | uuid・`vehicles` への外部キー | 改造した車両。編成でなく車両に付けるので、組み換えても記録は車両と一緒に移る |
| `modified_on` | date・NULL 可 | 改造した日。NULL は「新製のときから」（新製の日が分からない車両の最初の塗装など） |
| `kind` | varchar | 改造の種類。`livery`（塗り替え）・`exterior`（外観の変更）・`renewal`（リニューアル）・`equipment`（機器更新）・`platform-door`（ホームドア対応）の 5 つにする。種類は増やしすぎない（2026-11-24 ユーザー）。`exterior` は前灯の移設・前面の作り替えのような、塗装以外で見た目が変わる改造。パンタグラフの統一のような機器の改造は `equipment` に入れる。細かい中身は `description` に書く。絵は前灯を描かないので、`exterior` は経歴に出るだけで絵は変えない |
| `value` | varchar・NULL 可 | 種類ごとの値。`livery` では塗装の値（上の表）。ほかの種類では使わなくてよい |
| `description` | text・NULL 可 | 中身の説明（「VVVF を SiC に更新」など）。日付が月までしか分からないときは、その旨もここに書く |
| `created_at`・`updated_at` | timestamptz | |

- 作り方の比較（2026-11-23 ユーザーが A を選んだ）
  - A（採用）：改造を「起きた日」の出来事として 1 行ずつ持つ。ある日の状態は、種類ごとにその日までの最新の行で決まる。塗り替えても前の行を直さなくてよい
  - B：どの種類も開始日と終了日の期間で持つ。リニューアルのように終わりの無い改造に合わず、塗り替えのたびに前の行を閉じる手間がある
  - C：塗装の表（期間）と改造の表（出来事）に分ける。表と api が 2 つずつになり、前面の形が変わるリニューアルをどちらに入れるか迷う
- 集約ルートは編成にする（2026-11-24 ユーザー「formation→vehicle→modifications でいいけど保存単位は formation にしなさい」）。記録は車両に付けるが、読むのも保存するのも編成を通す。改造の記録を車両や記録の単位で保存する口（リポジトリ・api）は作らない。保存は、編成の集約（編成 → 号車 → 車両 → 改造の記録）をまとめて 1 回で書く
- migration は generate で作る。本番への適用はユーザーが行う
- 段 1 では書き込みの api は作らない。値はユーザーが SQL で入れる。書き込みの api は次の段の管理画面で作り、上の保存単位に従う
- 編成の取得の `include` に `vehicleFormations.vehicle.modifications` を足し、車両ごとの記録を返す。並びは `modified_on` の古い順（NULL を先）にする
- 期間の取得（`from/:startDate/to/:endDate`）は 31 日までしか取れない（`PERIOD_MAX_DAYS`。2026-11-14 の入力検証の見直しで入った）。そこで、編成番号ごとに全期間を返す取得 `GET /v3/formations/number/:formationNumber` を足す（2026-11-24 ユーザー了承。始めは全期間を期間の取得で取って client で絞る案だったが、この制限で取れなかった）
  - 返すのは、その編成番号の期間の行すべて。並びは始まりの日の古い順で、空の始まりの日が先
  - `include`（`agency`・`vehicleFormations.vehicle.modifications`）と `fields` は期間の取得と同じものを使える
  - 無い編成番号なら空の配列を返す。編成番号の形（数字と英字だけ、長さの上限）は検証する
  - client はこれを編成番号が変わったときに 1 回だけ呼ぶ
- 表と include は api PR #220（merge 済み）。編成番号ごとの取得は別の api の PR にする。どちらも client の PR より先にデプロイする

### 期間の目撃の絞り込み

`GET /v3/operation-sightings/from/:start/to/:end` に、省略できる引数 `formationNumber` を足す（api PR #219・v4.9.0 で済み）。

- 推定（`includeCarriedOver=true`）は、その日の全編成の目撃を材料に組み立てている。絞り込みは SQL の WHERE でなく、直接の目撃と推定を合わせて並べたあとの結果にかける。材料は絞らない
- `includeCarriedOver` が無いときは、直接の目撃の取得を SQL で絞ってよい
- `fields` と `include` は今までどおり効く
- 無い編成番号を渡したら、空の配列を返す
- 既存の呼び出し（引数なし）の結果は変えない

一度に取る範囲は 1 か月（最大 31 日）。過去の運用が 30 日を取っているので、重さは同じ程度と見込む。
