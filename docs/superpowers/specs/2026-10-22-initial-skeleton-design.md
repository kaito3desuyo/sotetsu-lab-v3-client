# 初回読み込みの骨組みを全ページへ広げる 設計

- 日付: 2026-10-22
- ブランチ: `fix/initial-skeleton`
- 元になった作業: リアルタイム運用情報の CLS 修正（PR #261・v2.15.2）と二重描画の解消（PR #262・v2.15.3）

## 目的

リアルタイム運用情報で入れた初回読み込みの表示を、データを取る全ページへ広げる（ユーザー判断）。

- データが届く前は、届いた後と同じ高さを取って骨組み（skeleton）を出す
- 後から出る絞り込みのチップも骨組みにする
- 取る前に「ありません」や仮の値（運用群の「休」だけ等）を出さない

docs/design.md の掟「取得中は骨組みを出す」「骨組みは届いた後と同じ高さを取る」を、全ページで守る状態にする。

## 決定事項

### 1. 共通部品は小さく 2 つ、形はページごと（案 A・ユーザー判断）

`src/app/shared/skeleton/` に置く。

- `app-skeleton-bar`（`SkeletonBarComponent`）
  - 灰色の棒 1 本。ホストに `tw-block tw-animate-pulse tw-rounded-control tw-bg-paper-3 motion-reduce:tw-animate-none` を付ける
  - 幅・高さ・角の丸みは、使う側がホストの `class` で渡す（例: `<app-skeleton-bar class="tw-h-5 tw-w-24">`）
  - 1 本だけでは読み上げない（`aria-hidden="true"`）。読み上げは包む側の `aria-label="読み込み中"` に任せる
- `app-skeleton-chips`（`SkeletonChipsComponent`）
  - `input.required<readonly string[]>()` の `widths`（Tailwind の幅の class）を受け、高さ 42px の行に高さ 32px のチップの形を並べる
  - 行に `aria-label="読み込み中"` と `data-testid="filter-chips-skeleton"` を付ける
  - リアルタイムの絞り込みにある `<ng-template #chipsSkeleton>` をこれに置き換える

骨組みの形（行の数・並び・高さ）は各ページが自分の本物に似せて組む。案 B（汎用 1 種類）・案 C（ディレクティブで包む）は、届いたときに形が変わり CLS が残るので採らない。

リアルタイムの `operation-real-time-skeleton-ledger` は形が専用なのでページに残し、中の棒を `app-skeleton-bar` に置き換える。ダッシュボードの骨組みも `app-skeleton-bar` に寄せる。

### 2. 取ったかどうかはストアのフラグで見分ける

- 各ページのストアに `hasFetched…`（既定 `false`）と `setHasFetched…(value: boolean)` を足し、`hasFetched…$` を select で出す。空配列では「取る前」と「0 件」を見分けられないため（リアルタイムと同じ）
- 条件ごとに取り直すページ（運用表・運用行路図・駅別時刻表など、URL の条件で `fetchData()` を呼ぶページ）は、`fetchData()` の始めで `false`、取得が終わったら成功・失敗を問わず `true` にする。失敗で骨組みが出たまま止まらないように。リアルタイムは今のまま（setter で `true`）
- テンプレートは `@if (!hasFetched…()) { 骨組み } @else if (0 件) { app-empty-state } @else { 本物 }` の順にする
- `isLoading()` で本物を消す書き方（運用表・列車位置情報の `@if (!isLoading())`）はやめる。毎秒・投稿後の取り直しで中身が消えてずれるため
- **検索の条件を変えて取り直すとき**（駅・方向・ダイヤ・日付・日数・運用を変えたとき）は、取る前にフラグを `false` に戻し、骨組みを出し直す。古い結果を新しいものと見間違えないため
- 同じ条件の取り直し（自動更新・投稿後・ソケット）はフラグを戻さない。中身を出したまま差し替える
- 保存されたストアの扱いは各ページの今の振る舞いを保つ。保存の範囲は変えない（ストア全体の保存は通信断のため）
  - 運用表は今も取得中はカードを出さない（ダイヤを替えたとき前のダイヤのカードが混ざらないように）。これを骨組みに置き換える。取れなかったら、保存していたカードを出す
  - リアルタイム・ダッシュボードは、再訪では保存した中身をすぐ出す。骨組みは初回だけ
  - 列車ダイヤグラムは列車のデータを保存していない（保存は操作帯の開閉だけ）。だから入ったときとダイヤを変えたときに骨組みを出す。路線・方向だけを変えたときは図を出したまま（2026-10-22 PR3 で実装して分かった）

### 3. 高さの決まり

- 長さが決まらない一覧・表は、画面からヘッダーを引いた高さを取る: `tw-h-[calc(100dvh-48px)] md:tw-h-[calc(100dvh-64px)]`（リアルタイムと同じ）
- 大きさが決まっているもの（絞り込みの行・図の枠・凡例）は、本物と同じ高さにする
- 骨組みの行は本物の行と同じ高さにする（リアルタイムの帳票は 67px）

### 4. ページごとの形

| ページ | 対象の部品 | 骨組みにするもの |
|---|---|---|
| 運用行路図 | `operation-route-diagram-route-filter`・`operation-route-diagram-drawing`・ページ | 路線の絞り込みの行（`app-skeleton-chips`）、図の枠（ダイヤ名の帯＋図の高さ） |
| 運用表 | `operation-table-filter`・ページ | 運用群のチップ、縦カードの一覧（画面 1 枚分） |
| 駅別時刻表 | `timetable-station-table`・ページ | 時刻の格子（時の列＋分の並び・画面 1 枚分）。取る前の「ありません」をやめる |
| 全線時刻表 | `timetable-all-line-route-filter`・`timetable-all-line-table`・ページ | 路線の絞り込みの行、表（駅の列＋列車の列・画面 1 枚分） |
| 過去の運用 | `operation-past-time-table`・ページ | 表（編成の列＋日付の列・画面 1 枚分）。途中の高さで一度出るのをやめる |
| 列車位置情報 | ページ・`train-location-line` | 路線図の場所（画面 1 枚分） |
| 列車ダイヤグラム | `train-diagram-legend` | 凡例の項目（本物と同じ 1 行） |
| 列車情報の入力（更新・コピー） | ページ・`timetable-edit-form-trips` | 既存の列車を取るまでのフォームの行 |
| ダッシュボード | `dashboard-status-card`・`dashboard-latest-sightings` | 形は変えず `app-skeleton-bar` に寄せる |

形の細部（行の数・棒の幅）は、実装のときに本物の画面を測って決め、ユーザーに画面で見せる。

### 5. 変えないもの

- 読み込みが終わった後の見た目（位置・大きさ・色）。各ページはロック済み
- リアルタイムに残っているカードの高さの変化（約 0.05）
- 車両のページ

## 確かめ方（受け入れ条件）

1. jest: ページごとに次の 3 つを書く
   - 取る前は骨組みが出て、`app-empty-state` は出ない
   - 取った後は骨組みが消える
   - 0 件のときは `app-empty-state` が出る
   - 条件を変えて取り直すときは、骨組みに戻る（条件のあるページ）
2. CLS: 手元で、スマホ 390×844 と PC 1440×900 を各 3 回測り、直す前と後を比べる。対象の全ページで 0.1 未満にする。列車ダイヤグラムとダッシュボードは今の値を上回らない
3. 読み込みが終わった後の主な要素の位置と大きさが本番と一致する（getBoundingClientRect で比べる）。画面も目で見る
4. 入力画面は、ユーザーにログインしてもらって測る（保存テストのダイヤ: 渋谷工事臨時ダイヤ）
5. jest 全件・変更したファイルの eslint が通る
6. docs/design.md の各ページの「ロック後の改訂」に書き足す

## 出し方

PR を 3 つに分ける。CLS の大きい順。

- PR1: 共通部品（リアルタイムの置き換えを含む）＋運用行路図・運用表・駅別時刻表
- PR2: 全線時刻表・過去の運用・列車位置情報
- PR3: 列車ダイヤグラム・列車情報の入力・ダッシュボード

コミットは `fix: :bug:`（ずれと誤表示の修正）。共通部品の追加とリアルタイムの置き換えは `refactor: :recycle:`。
