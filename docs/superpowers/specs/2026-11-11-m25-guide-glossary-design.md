# M25 使い方と用語 設計

2026-11-11。ロードマップの M25「使い方と用語」の client 側。api は変えない。

## なぜ作るか

ユーザーの言葉: 「使い方がわからない」「使い方がわかるようになってほしい。相鉄の運用の流れを理解してほしい」。

GA の実測（2026-10-14〜11-10 の 28 日、新しく来た人 847 人）:

| 最初のページ | 人数 | 滞在 | ページ数 |
|---|---|---|---|
| トップ `/` | 473 | 平均 7.5 分 | 6.6 |
| リアルタイム運用情報 | 108 | 8.3 分 | 6.1 |
| 運用表・全線時刻表・駅別時刻表・行路図・過去の運用・時刻表の編集画面など | 約 120 | 3〜30 秒 | ほぼ 1 |

- 10/14〜10/31 に初めて来た 595 人のうち、また来たのは 130 人（22%）。
- Google 検索から来た新しい人の 9 割は使っているが、直接来た新しい人は 4 割。
- 新しい人で投稿フォームを開いたのは 24 人、投稿できたのは 20 人。

困っている人は 2 種類いる（ユーザー確認「両方では？」）。

- **A: 奥のページに直接入って迷子になる人。** 検索から運用表や時刻表の編集画面にいきなり入り、何のサイトか、何を見るページかが分からずに去る（推測）。
- **B: トップから入って使ってはいるが、意味が分からない人。** 運番・運用・「?」・順送りなどが分からず、「自分の乗った電車の編成」までたどり着けないので、また来る理由ができない（推測）。

## 目標と、目標でないもの

目標:
- どのページからでも「このページの見方」と「使い方」「用語集」にたどり着ける。
- 使い方を読めば、相鉄の運用の流れ（運用・運用番号・運用群・編成・目撃・推測・順送り・同日引き継ぎ・出庫と入庫）が分かる。

うまくいったかの見方（GA。前後の 28 日で比べる）:
- 新しく来た人の再訪の割合（今は 22%）。
- 奥のページから入った新しい人が 2 ページ目に進む割合。
- 「?」が押された回数と、そこから使い方・用語集へ進んだ回数。

目標でないもの:
- 既存の画面の情報を減らすこと、作り直すこと（デザイン改修の原則「情報削減禁止」）。
- api の変更。

やってはいけないこと:
- 常連の邪魔になる案内（毎回出るポップアップ、一覧を押し下げる大きな説明の枠）。
- 運用の説明で事実を間違えること。分からないところは下書きで「要確認」と印を付け、ユーザーに直してもらう。

## 直通先の各線での扱い（ユーザー指示 2026-11-11）

ユーザーの言葉:「東急、東京メトロ、都営等の直通先各線での取り扱いについても書いておいたほうが良いだろう（私は詳しくは知らない）」。

使い方と用語集に、直通先の各線（JR・東急・東京メトロ・都営・埼玉高速・東武・西武など）で運用番号がどう扱われるかを書く。ユーザーも詳しくは知らないので、次の 2 つを分けて書く。

- **このサイトでの扱い**: 相鉄の運用番号（G・K の付いたものを含む）で、直通先を含めた 1 日の行路をまとめて見せている。例: 行路図・運用表に、大宮・西高島平・南古谷などの直通先の駅が出る。目撃も、直通先で見たものを相鉄の運用番号で投稿する。これはコードと本番のデータで確かめてから書く。
- **各社での実際の扱い**（各社が自社の線内で別の運用番号・運行番号を使っているか、など）: 下書きの前に調べる。調べる先は、公式の資料よりも鉄道ファンのサイト（運用情報のサイトなど）を優先する（ユーザー指示 2026-11-11「公式の資料よりも、ファンサイトを探したほうが良い」）。どのサイトから取ったかを控えておき、複数のサイトで食い違う所や 1 つでしか見つからない所は、そうと分かるように印を付ける。見つからない所は推測で埋めない。調べた結果はユーザーが読んでから出す。

## 運用番号の見分け方（ユーザー説明 2026-11-11）

使い方（特に投稿のところ）に、見た列車の運用番号をどう知るかを書く。

- 相鉄・東急・地下鉄の線内では、基本的に先頭車に運用番号が書いてある（表示されている）。
- JR の線内では、先頭車のその場所に列車番号が書いてある。運用番号は書いていない。
- 東武・西武の線内でどうなるかは、ユーザーも知らない。ファンサイトで調べ、見つからなければ使い方に書かない（推測で書かない）。
- だから JR の線内で見たときは、列車番号や時刻から運用番号を引く。投稿フォームの「列車から選ぶ」（M30）を使えば、駅と時刻から列車を選んで運用番号を入れられる、と案内する（Claude の案）。
- 「基本的には」とのことなので、例外があり得る。先頭車のどこにどう出るか（行先表示の横の小さな表示など）の細かい書き方は、ファンサイトで確かめて、要確認として扱う。

調べた結果（2026-11-11。ファンサイト・Wikipedia と、画像検索で元の写真を開いて読んだもの。詳細と出典は作業メモ `.context/m25-through-service-research.md`。使い方の文に出典を載せるかは作る人が決める）:

- JR 車は、窓の内側の左下の同じ表示器に、相鉄線内では運用番号（例「86」）を、JR 線内では列車番号（例「1388F」）を出す（写真 3 枚で一致）。
- 相鉄車は東急線内でも「2 桁＋G」、東急車は「2 桁＋K」を窓の左上に出す。地下鉄の線内も同じ「2 桁＋記号」を通しで使う（S＝東京メトロ・T＝都営・M＝埼玉高速。東横線系では M＝西武・T＝東武）。
- 相鉄車は東武・西武の線内には入らない（Wikipedia の 2 ページで一致）。東武・西武の線内で東急車などが運用番号を出す写真は 2 枚あるが、団体臨時と場所が断定できないもので、ふだんの列車でもそうかは確かでない。使い方には「確かでない」と書くか、書かない。

## 運用群の表について

画面での群の名前と並びは、client の「運用群」の表示規則（docs/design.md）に合わせる。用語集の運用群の表は今のダイヤの群を載せ、過去の群（2・4・9 群、5G・8G）は表の下に 1 行ずつ添える。

## 作るもの

### 1. ヘッダーの「?」と「このページの見方」

- ヘッダー（`layout/components/header`）のアカウントのボタンの左に、`mat-icon-button`（アイコン `help_outline`、`aria-label="このページの見方"`）を置く。
- 押すと下から出るシート（Material の Bottom Sheet）に、次を出す。
  - 見出し「（ページ名）の見方」
  - 説明 3〜5 行
  - 「使い方 ›」「用語集 ›」のリンク
- 説明はページごとに持つ。説明の無いページ（ログイン・メンテナンス・404 など）は、サイトの一言説明とリンクだけを出す。
- 説明を書くページ: トップ、全線時刻表、駅別時刻表、時刻表の追加・編集・コピー、列車ダイヤグラム、列車位置情報、リアルタイム運用情報、過去の運用情報、運用表、行路図、相鉄の車両、マイページ、投稿管理、登録。
- 制約: ヘッダーは 320px で要素の合計がちょうど画面の幅になっている（header.component.html のコメント）。ボタンを足しても、ページ名が折り返さず、ヘッダーからはみ出さないこと。320px・360px・390px の実物で確かめる。

### 2. 使い方のページ `/guide`

1. **相鉄の運用の流れ**: 図を 1 枚付けて短く説明する。
   - 運用と運用番号
   - 運用群と車両の会社
   - 編成
   - ダイヤで決まっていることと日ごとに変わること
   - 目撃
   - 推測の「?」（順送り・同日引き継ぎ）
   - 出庫 ○ と入庫 △
   - 直通先の各線での扱い（上の「直通先の各線での扱い」）
2. **やりたいこと別の使い方**:
   - 今どの編成がどこを走っているか → リアルタイム運用情報・列車位置情報
   - ある運用の 1 日の行路 → 運用表・行路図
   - 時刻表から列車を探す → 全線時刻表・駅別時刻表・列車ダイヤグラム
   - 過去の日の運用 → 過去の運用情報
   - 見た編成を投稿する → 投稿フォーム（登録が要る）
3. 用語集へのリンク。

### 3. 用語集のページ `/glossary`

- 用語ごとに見出しを付け、ページ内リンク（`#順送り` など）で飛べるようにする。
- 載せる用語: 運用、運用番号（運番）、運用群、編成、目撃、推測の「?」、順送り、同日引き継ぎ、不明、出庫 ○、入庫 △、休車（100）、直通（直通先の各線での扱いを含む）、種別。
- 画面に出ている記号（◆ など）は、実際の画面を見て拾い、載せる。

### 4. 置き場所と検索

- サイドナビの「このサイトについて」の見出しの下に、「使い方」「用語集」を足す。
- 2 ページとも sitemap に足す（公開ページを足したら sitemap も足す決まり）。
- SSR で描く（他の公開ページと同じ）。

### 5. 計測

- GA のイベントを足す。
  - 「?」を押した: `help_open`（どのページか）
  - シートからリンクで進んだ: `help_link`（行き先）
- 前後の比べ方は「目標と、目標でないもの」の見方に従う。

## 私（Claude）の判断で決めたこと

- 使い方と用語集は、免責事項と同じく HTML で直に書く。Markdown を描く仕組みは入れない（依存を増やさない）。
- URL は `/guide` と `/glossary`。既存の `/privacy-policy`・`/disclaimer` と同じく 1 段にする。
- ページ名は「使い方」「用語集」。
- イベント名は `help_open`・`help_link`。どのページかは、ルートのパスの型（`/operation/real-time` のように、`;` の行列パラメータを落としたもの）で送る。既存の GA のイベントの書き方に合わせる。
- 「?」は、説明の無いページ（ログイン・メンテナンス・404 など）も含め、ヘッダーのある全ページに出す。時刻表の追加・編集・コピーは、説明を 1 つで共有する。
- 運用の流れの図は概念図にする。運用 → 編成 → 目撃 → 推測の関係と、順送りの輪を、1 群（11〜16）の実際の番号で例示する。固定の図で、320px で読めること。
- 用語の正（根拠）:
  - 推測の「?」・同日引き継ぎ・不明は、api の spec `docs/superpowers/specs/2026-10-19-sighting-run-assignment-design.md` と `sighting-carry-over.read-model.ts`。
  - 順送りは api の `operation-number-circulation.ts`。
  - 出庫 ○・入庫 △ と画面の記号は、client の docs/design.md と画面。
  - client の表示と api の規則が食い違ったら、api を正として書き、食い違いはユーザーに報告する。

## 作る人に任せること

- 「このページの見方」の説明を、どこにどの形で持つか（ルートの data か、ページの名前で引く表か）。
- 運用の流れの図の描き方（SVG か HTML か）。
- シートの細かな見た目。既存の部品とデザイン原則（docs/design.md）に合わせる。

## 文の下書きの扱い

- **出し方は一度に出す**（ユーザー決定 2026-11-11）。1 本の PR で作り、ユーザーが文をすべて直し終えるまでマージしない。「要確認」が 1 つでも残っていればマージしない。

- 説明文は、コード・docs/design.md・本番のデータ・この設計書の「ユーザーが決めたこと」を元に下書きする。
- 事実に自信の無い所は、下書きの中で「要確認」と印を付け、ユーザーに直してもらってから出す。
- 表の「要確認」の欄も同じ。
