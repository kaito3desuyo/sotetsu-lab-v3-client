# M30 投稿のしやすさ 設計

2026-11-10・ブランチ `feature/m30-post-ease`。ロードマップ（`docs/roadmap.md` の M30）の client 分。api は変えない（下の「api の M30」）。

## 何のためか

ホームで列車を見てスマホから投稿する人が、**編成番号と運用番号を覚えておく手間**を減らす（ユーザーの言葉: 「編成番号と運用番号を覚えとくのが大変」）。

- 運用番号は相鉄線内なら先頭車の表示で分かるが、見てから打つまで覚えておく必要がある。**直通先では表示されない**ので、見ただけでは分からない（ユーザー）。
- 駅・時刻・行先・種別は、その場にいれば簡単に分かる（ユーザー）。
- 投稿する人がまず開いているのはリアルタイム運用（ユーザー）。利用はスマホが 75%（GA 2026-10-13〜11-09）。

そこで「その場で分かる情報で列車を選ぶと運用番号が埋まる」入口を足す。編成番号は車体を見れば分かるので手で打つが、候補を出して打つ量を減らす。

## 成功の基準

2 週間後の GA で、**新しく足した入口が使われていること**（ユーザーが選んだ基準。投稿失敗率の低下は基準にしない）。そのために投稿のイベントに「どこから開いたか」「運用番号を列車から選んだか」を載せる（下の「計測」）。

## やらないこと・やってはいけないこと

- **api の検証の境目（未来の時刻・始発の 30 分前）は緩めない。** 端末の時計のずれを許す幅も入れない。
  - 根拠（2026-11-10 の実測）: 「未来の時刻は指定できません」226 件のうち約 150 件は Windows の 1 人。投稿管理の手がかりから Windows の投稿を抜くと、「現在時刻」で送った投稿の（受け取った時刻 − 目撃時刻）は全部 +0.07〜2.5 秒で負は 0 件＝時計は進んでいない。失敗は「時刻指定」でまとめて入れている時間帯（11/6 7 時台: 18 件中 17 件が時刻指定、同時間帯に GA の失敗 8 件）に出ている。先回りの推測投稿か打ち間違いかは見分けられないが、どちらでも検証は正しく効いている。
- **運用番号の欄は手で打つまま**（2026-08-22 のユーザー判断「選ぶより打つほうが速い」を保つ）。選ぶ入口は足すだけ。
- **入口から開くとき、時刻は埋めない**（ユーザー決定）。運用番号だけ埋め、時刻は「現在時刻」のまま。
- **編成番号の候補に「その運用に充当していると推測される編成」を出さない**（ユーザー決定）。見ずに推測のまま投稿されるのを避ける。
- 列車・行先・種別などの情報は削らない（design.md・情報削減禁止）。
- 休車（運用番号 100）は列車を持たないので、列車から選ぶ一覧には出ない。

## 作るもの

### 1. 投稿フォーム: 運用番号の欄の横に「列車から選ぶ」

対象は共通の `shared/operation-post-card/operation-post-form.component`（トップの投稿カードとリアルタイム運用の投稿ダイアログの両方）。ユーザーが案 A1〜A3 から **A2** を選んだ（スマホで縦を増やさない・フォームは今のまま）。

- 運用番号の欄の横にボタン「列車から選ぶ」。
- 押すと、フォームのあった場所の中身が「列車を選ぶ」画面に入れ替わる（ダイアログならダイアログの中、トップのカードならカードの中）。選ぶか戻ると、フォームに戻る。入力途中の値は消さない。
- 「列車を選ぶ」画面:
  - **いる駅**の選択。前回選んだ駅を端末に覚える（`withSettingsStorage` か `DeviceStorage`。私の判断）。初めて開いたとき（前回の駅が無いとき）は駅を空にして、駅を選ぶよう促す（私の判断）。駅の選び方・並びは他ページと同じ「会社名 路線名」（`buildStationGroups`・design.md「会社・路線の並び」）。
  - **上下**の切り替え（既定は両方。私の判断）。
  - 一覧: その駅の**今の前後 10 分**（私の判断）に発着する今日のダイヤの列車。1 行に「時刻（発。当駅止まりは着）・種別・列車番号・行先・運用番号」。時刻順。過ぎた列車は薄く。一覧は枠の中でスクロールし、今に一番近い列車が見える位置で開く。
  - 押すと運用番号の欄に入り、フォームに戻って**編成番号の欄にフォーカス**。
  - 該当が 0 本のときは、その旨と、前後の幅を広げる手段（例: 「もっと前」「もっと後」）を出す。
- 直通先の駅も出す。DB の `times` に直通先の駅の時刻がある（2026-11-10 確認: 東急 30 駅・東京メトロ 35 駅・JR 東日本 27 駅・都営 27 駅など）。一覧に出すのは**運用番号を持つ列車だけ**（押しても埋める番号が無いため。私の判断）。
- データは今日のダイヤ（`TodaysCalendarListState`）の運行を、駅別時刻表と同じ取り方（`TripBlockService.findManyByFilter`・`TRIP_BLOCK_TIMELINE_FIELDS`・`stationTrips`）で取る。**api は変えないのが前提**（私の判断）。計画の段階で両方向ぶんの大きさと時間を実測し、スマホで実用にならないと分かったときだけ、api に口を足す案を作ってユーザーに諮る。
- 4 時の境目（04:00〜翌 03:59 を 1 営業日）に従う。

### 2. 投稿フォーム: 編成番号の候補

- 欄は手で打つまま。打ち始めると、**今日走っている編成**（`TodaysFormationListState`）のうち、打った字で始まる（または含む）ものが下に候補として出る。所属を選んでいればその会社に絞る。押すと欄に入る。
- 候補の並びに推測の充当編成を混ぜない（上の「やってはいけないこと」）。
- 部品は Material（`mat-autocomplete` 想定。design.md の Material 部品優先）。

### 3. 投稿フォーム: 送る前の確認

送る前に client で確かめ、引っかかったら**欄の下に文言**を出して送らない（api の検証はそのまま残る。client は早く知らせるだけ）。

- 時刻指定の時刻が今より先 → 「未来の時刻は指定できません」と同じ意味の文言。4 時の境目の換算（今の `submit` の処理）を済ませた後の時刻で判定する。
- 運用番号が今日のダイヤに無い（`TodaysOperationListState`。100 は可）→ 止める。api も目撃時刻の営業日のダイヤで引く（`#resolveOperationContext`）。client の時刻指定は 4 時の境目の換算で必ず今日の営業日に収まるので、今日のダイヤの一覧で判定してよい。
- 編成番号が今日の編成に無い（`TodaysFormationListState`・所属と合わせて）→ **止めずに欄の下に注意だけ出し、送れるままにする**（私の判断）。api は「その日の編成番号、無ければその日の車両番号」で引く（`formationQuery.findOneByAgencyIdAndFormationNumberAndDate` → `…VehicleNumberAndDate`）が、client の今日の編成の一覧は車両番号を持たないため、車両番号での正しい入力を client だけで見分けられない。
- 始発の 30 分前より前は、始発時刻を client が持っていなければ確認しない（api に任せる）。持てるなら同じ境目で止めてよい（builder 判断）。
- 文言は api のエラー文言と意味をそろえる。

### 4. 各ページの入口（どれも運用番号だけ埋めて投稿ダイアログを開く）

開くのは既存の `OperationPostDialogService.open({ operationNumber })`。対象のページはどれもロック済み（design.md「ロック済みページ」）なので、**先に design.md の該当ページの節に入口を書き足してから**ページに反映する。

- **列車ダイヤグラム**: 列車を押すと出る情報カード（`train-diagram-info-panel`）に「投稿」ボタン。運用番号があるときだけ。
- **列車位置情報**: 図のカード（`train-location-card`）はカード全体がリンクなので触らない。駅の欄（`train-location-station-panel`）の「次に来る列車」の各行に「投稿」ボタン。運用番号があるときだけ。
- **駅別時刻表**: セル（`timetable-station-trip-cell`）の左の列、充当編成番号の字（「10701?」「不明」）は**そのまま残し**、別に小さな投稿ボタンを置く（ユーザー: 「ボタンにはしたい」「編成番号と投稿ボタンは分けたい」）。アイコンだけのボタンで編成番号の下（私の判断）。今日のダイヤで充当編成を出しているとき（`showCurrentFormation`）だけ。セルの高さが変わるなら `utils/station-row-height.util.ts` の見積もりも直す。見た目は**実装した後に実物（手元・実データ）でユーザーに見せて**決める（私の判断）。直しが入る前提で計画に余裕を取る。
- 投稿できない人（viewer・フラグ on のゲスト）への出し方は、今のダイアログの振る舞い（案内を出す）に任せてよい。

### 5. 計測

GA の `sighting_form_start`・`sighting_submit`・`sighting_submit_success`・`sighting_submit_failure` に次を載せる（パラメータ名は builder が決める・GA のカスタム定義の追加はユーザー）。

- 開いた入口: トップのカード・リアルタイムの投稿ボタン・リアルタイムの運用カード・リアルタイムの編成カード・列車ダイヤグラム・列車位置情報・駅別時刻表。
- 運用番号を「列車から選ぶ」で入れたか。
- 現在時刻か時刻指定か。
- 「列車から選ぶ」を開いた・列車を押した、のイベント（新しいイベント名は builder が決める）。
- 開いた入口は `OperationPostDialogService.open()` の引数（`OperationPostInitialValue` の隣）に足してフォームまで渡す（私の判断）。トップのカードはカード自身が入口。

## api の M30

api の roadmap の M30（「検証の境目と文言を client とそろえる」「原因が端末の時計のずれなら許す幅を決める」）は、上の実測で**時計のずれではない**と分かったので、境目は変えない。client が api の文言に合わせる。api のコードは触らない。api の roadmap の M30 の行は、この結論で書き直す（docs だけ）。

## 出し方

- **1 から 5 まで全部を 1 本の PR で出す**（ユーザー決定）。
- ロック済みの 3 ページは、design.md の各ページの節への書き足しを実装の最初の作業として同じ PR に入れる。ユーザーは PR の差分で読む（私の判断）。

## builder に任せること

- 「列車を選ぶ」画面の部品の分け方・置き場所（`shared/` の新しい部品になる想定）・データの取り方とキャッシュ。
- ボタンの文言・アイコン・見た目の細部（design.md の掟と Material の部品に合わせる）。
- 前後 10 分の幅を広げる手段の形。
- GA のパラメータ名。

## 確かめ方

- jest に加え、実データで見る（`feedback_visual_realdata_gate`）: スマホ幅 390px で、リアルタイムのダイアログから「列車から選ぶ」→ 駅 → 列車 → 運用番号が入り編成番号にフォーカス、まで。直通先の駅でも。
- 3 ページの入口は、ロック済みの見た目が崩れていないかを実物で確かめる。駅別時刻表のボタンはユーザーに見せる。
- 送る前の確認は、未来の時刻・無い運用番号・無い編成番号で止まり、正しい車両番号は止めないこと。
