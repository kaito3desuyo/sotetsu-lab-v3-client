# 画面の文言の文体を少し硬くする

## 目的

アプリ全体の画面の文言を、今より少し硬い文体にそろえる（ユーザー指示 2026-11-18「アプリケーション全体として、文章の文体をもう少しお固めにしてほしい」）。

今の文言は、文末はすべて「です・ます」で、「〜ね」「〜よ」「！」は無い。柔らかく感じさせているのは言葉の選び方で、「出ます」「移ります」「押す」「みんなの」「〜の人」のように、話し言葉に近い和語で書いてある。これは、画面の文を natural-japanese と yomiyasu で推敲してきた結果でもある。

## 決めた文体

ユーザーが 3 段階の改稿例から B（です・ますのまま、書き言葉の硬い言い回しにする）を選び、「1mm ぐらい硬すぎ」として 1 段戻した形に決めた（2026-11-18「丁度良い」）。決めたときの例文を次に挙げる。

| 今 | 決めた形 |
|---|---|
| 運用番号を押すと、その運用の行路図に移ります。 | 運用番号を選択すると、その運用の行路図へ移動します。 |
| 上の帯を開いて、編成番号と日付を選びます。駅を選ぶと、その駅を通る列車だけに絞れます。 | 上部の帯から編成番号と日付を指定してください。駅を指定した場合は、その駅を通る列車のみを表示します。 |
| 編成番号に「?」が付いたものは、目撃ではなく推測した編成です。途中で編成が替わった日は、替わった所に「… に差し替え」の行が出ます。 | 「?」付きの編成番号は、目撃情報に基づかない推定です。運用の途中で編成が差し替えられた場合は、その箇所に「… に差し替え」の行を表示します。 |
| ダイヤ通りに走った場合の位置で、実際の遅れは入っていません。 | 表示位置はダイヤどおりに運行した場合のもので、実際の遅延は反映されていません。 |
| manager の人は、ここからその投稿者を BAN できます。BAN された人は投稿できなくなります。 | manager 権限を持つ利用者は、この画面から投稿者を BAN できます。BAN された利用者は投稿できなくなります。 |
| 車庫に入らずに、同じ車両のまま別の運用へ移る・別の運用から移ってくる所の印です。 | 入出庫を伴わずに、同一車両が他の運用へ移行する箇所、または他の運用から移行してくる箇所を示す記号です。 |

決まりにすると次のとおり。

- 文末は「です・ます」。「である」調にはしない
- 動作と状態は、定着した漢語で書く。表示する・選択する・指定する・移動する・反映する・変更する・推定・目撃情報・充当・箇所・区間・記号・利用者・現在・のみ
- 次の言い方は柔らかすぎるので使わない。「出る」（→表示される）、「移る」（→移動する）、「押す」（→選択する）、「入っている」（→充当されている）、「みんなの」（→利用者の）、「〜の人」（→利用者・権限を持つ利用者）、「いま」（→現在）、「替わる」（→変更される・差し替えられる）、「だけ」（→のみ）、「所」（→箇所）、「印」（→記号）
- 次の言い方は硬すぎるので使わない。「当該」「該当する」（→その）、「本サイト」「本画面」（→このサイト・この画面）、「経由する」（→通る）、「以後の」、「〜であるほど」
- 意味の分からない硬さにはしない。読み手がふだん使わない漢語（「拡充」「失効」など）に置き換えて、かえって読みにくくなるなら、今の言葉を残す

この決まりは client の `docs/style-profile.md` に書き、client の `CLAUDE.md` から指す。natural-japanese は、プロジェクトのルートか利用者が指定した場所にある `style-profile.md` を読んで書く（SKILL.md §1「文体プロファイル」）。`CLAUDE.md` に「画面の文言は `docs/style-profile.md` に従う」と書いておけば、それが場所の指定になる。こうしておけば、今後の推敲でも口調が柔らかく戻らない。

## 範囲

利用者の目に入る文言と、読み上げられる文言をすべて対象にする。

- ヘッダーの「?」の説明文、使い方、用語集
- ボタン・ラベル・欄の説明・空の表示・案内の文
- エラー・完了の通知（snackbar など）
- `aria-label` などの読み上げ用の文言
- ページの `title` と meta の description（`index.html` の分も含む）
- メンテナンス中・読み込みの失敗・ページが見つからないときの画面

対象にしないもの。

- コードのコメント、テストの名前、docs/ の文書
- 画面に出ない文字列（GA に送るイベント名や値、ログ）
- API が返して、そのまま画面に出すメッセージ。api のリポジトリの側で決まる
- 免責事項・プライバシーポリシー。もとから「前各号に定める」のような規程の書き方で、これより硬くする余地が無い。手を入れると意味が変わるおそれだけが残る（私の判断）
- ユーザーがこれまでに決めた語。帯の「開く」「畳む」、「運番変更」、ページの名前、ナビの項目名は変えない
- 1 語のボタンやラベルで、今の語が短く定着しているもの（「保存」「検索」「戻る」など）。決まりの「使わない言い方」に当たるときだけ直す
- 目撃・運用・列車番号のような、このサイトの用語そのもの

## 進め方

1 本の PR にまとめ、場所ごとにコミットを分ける（ユーザー判断 2026-11-18、3 案から 1 を選んだ）。

検討した案は次の 3 つ。

1. 1 本の PR で全部直す（選んだ案）。口調が一度にそろい、版上げも 1 回で済む。差分は大きくなる
2. 場所ごとに PR を分けて順に出す。1 本ずつは見やすいが、出し切るまで古い口調と新しい口調が混ざり、版上げが 4 回になる
3. 決まりだけ先に置き、直すのは触った所から。手間は少ないが、口調がそろうのはずっと先になる

文言を直すだけで動きは変わらないので、分けても危うさは減らない。それで 1 を選んだ。

コミットは次の単位に分ける（実装する人の判断で細かくしてよい）。

1. `docs/style-profile.md` と `CLAUDE.md` の追記
2. ヘッダーの「?」の説明文、使い方、用語集
3. 時刻表・運用・列車位置・ダイヤグラムなど、閲覧のページの文言
4. 投稿・ログイン・登録・マイページ・投稿管理の文言
5. 共通の部品・通知・エラー・空の表示
6. title・meta

文言を見ている spec は同じコミットで新しい文言に直す。文言は今ある場所（html と ts）で直し、定数にまとめたり i18n にしたりはしない（私の判断。今回の目的は口調で、仕組みは変えない）。

語を一括で置き換えず、1 文ずつ読んで直す（私の判断）。「だけでなく」「見るだけで」のように、「のみ」に替えると不自然になる使い方があるためだ。決まりの語を grep で探すのは、直し漏れを見つけるためだけに使う。

PR の squash のタイトルは `refactor: :pencil2: 画面の文言の文体を少し硬くする` にし、版は patch で上げる（私の判断。動きは変わらず、memory の決まりで refactor だけなら patch）。

## ロック済みのページ

リアルタイム運用情報（`/operation/real-time`）はロック済みで、見た目を変える前にユーザーに見せる決まりがある。文言を直すこともこれに含める。このページの文言は別のコミットに分けて最後に回す。コミットする前に、変わる文言を「今 → 直した形」の一覧にしてユーザーに見せ、了承を得てから入れる（私の判断。了承の前に入れると、戻す手間が出る）。

## 確かめ方

- 変えたファイルに関係する spec を `TZ=UTC npx jest --ci --watchAll=false --testPathPatterns=...` で流す（全体は流さない）
- eslint・prettier（ファイル単位）・`ng build` が通る
- 直した文を natural-japanese の lint と yomiyasu にかける。そのとき `docs/style-profile.md` を読ませ、和語に開く方向の指摘は決まりに従って退ける
- 手元の画面で主なページを開き、文が切れたりはみ出したりしていないかを見る。ボタンやチップは文字数が増えると幅が変わる
- 「使わない言い方」の語が画面の文言に残っていないかを grep で確かめる

## 実装する人に任せること

- 各文をどう書き換えるか。決まりと例文に沿っていれば、細かな言い回しは任せる
- 決まりに挙げていない語の扱い。迷ったら、上の例文の硬さに合わせる
